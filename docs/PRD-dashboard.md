## 1. 개요

### 1.1 배경·문제

plaud-obsidian-pipeline은 PLAUD 녹음기 오디오를 클라우드에서 받아(pull) → 전사(transcribe) → LLM 요약·교차검증 → 옵시디언 노트로 저장하는 무인 파이프라인이다. launchd 잡 3개가 전부이며 데몬·UI가 없다.

현재 운영 상태를 확인하는 방법은 이것뿐이다:

```bash
tail -f logs/pipeline.log
launchctl list | grep plaud-obsidian
cat state/pending_ids.txt
```

즉, "지금 정상인가?", "왜 이 녹음의 노트가 안 생겼나?", "실패한 건 어떻게 다시 돌리나?"에 답하려면 터미널에서 파일 여러 개를 직접 열어야 한다.

### 1.2 목표

**운영자 1인이 브라우저에서 30초 안에 다음 세 가지를 파악·조치할 수 있는 로컬 웹 대시보드.**

1. **정상인가** — 잡 3개가 살아 있고 큐가 비어 있는지
2. **뭐가 막혔나** — 보류(pending)·실패(failed)·건너뜀(skipped)·요약 미완(summary_pending)이 어디서 왜 생겼는지
3. **뭘 눌러야 하나** — 재시도·복구·수동 실행을 클릭 한 번(+확인)으로

### 1.3 비목표 (YAGNI — 이번 범위에서 제외)

- 다중 사용자, 로그인/인증 (localhost 1인 전용)
- 원격/외부망 접근, 모바일 앱
- 실시간 스트리밍 전사, 오디오 재생·편집
- 파이프라인 처리 로직 자체의 변경 (대시보드는 관측·조치 레이어)
- 노트 본문 편집 (편집은 옵시디언의 일)
- 알림 발송 (Slack/텔레그램 등 — 후속 검토)

## 2. 사용자·핵심 시나리오

사용자는 **운영자 1인** (파이프라인 소유자, 기술 이해도 높음, macOS 로컬에서 접속).

| # | 시나리오 | 대시보드가 해야 할 일 |
|---|---|---|
| S1 | **아침 상태 점검** — "어제 녹음 다 들어왔나?" | 홈 화면 한 장에서 잡 생존 + 단계별 카운터 + 최근 활동 확인 |
| S2 | **노트 미생성 추적** — "어제 회의 노트가 없는데?" | 녹음 id/파일명으로 추적: pending 큐인가, 전사 실패 격리인가, 요약만 실패(`summary_pending`)인가 |
| S3 | **실패 건 조치** — "격리된 파일 다시 돌리고 싶다" | 실패·보류 관리 화면에서 버튼 1회 + 확인 다이얼로그 |
| S4 | **설정 변경** — "pull 주기를 줄이고 싶다" | 설정 화면에서 값 수정, 부작용(플리스트 재생성 필요) 안내 |
| S5 | **노트 품질 점검** — "검증 안 된 요약이 몇 개지?" | 품질 뷰에서 `verified: false`·`summary_pending`·화자 미해결 노트 필터링 |

## 3. 데이터 소스 인벤토리

대시보드가 그릴 수 있는 정보의 전체 목록. 디자이너는 이 섹션을 "화면에 표시 가능한 재료 목록"으로 사용한다.

### 3.1 상태 파일 (`state/`)

| 파일 | 의미 | 포맷 | UI 표시 예 |
|---|---|---|---|
| `pulled_ids.txt` | 다운로드 완료한 녹음 id (누적) | 32-hex id, 한 줄 1건 (현재 136건) | "총 수신 136건" |
| `pending_ids.txt` | 서버측 오디오 미준비로 보류 중 | `id<TAB>시도횟수` — 96회(≈24h) 초과 시 skipped로 이동 | 보류 큐 테이블 + 진행바 `12/96` |
| `skipped_ids.txt` | 영구 건너뜀 (현재 1건) | id, 한 줄 1건 | 건너뜀 목록 + 복구 버튼 |
| `transcribe_failures.txt` | 전사 연속 실패 카운트 | `오디오파일명<TAB>횟수` — 3회 도달 시 `INBOX/_failed/`로 격리 | 실패 카운트 배지 `2/3` |
| `processed_notes.txt` | 노트는 생성됐으나 오디오 아카이브 이동 실패 | `오디오파일명<TAB>노트파일명` | "아카이브 재시도 대기 N건" 경고 |
| `.lock` / `.pull.lock` | flock 잠금 파일 (실행 중 판정용) | 0바이트 | "처리 실행 중" 라이브 배지 |

> **설계 원칙: 파일 없음 = 정상.** `transcribe_failures.txt`·`processed_notes.txt` 등은 건강한 상태에서는 존재하지 않는다. UI는 "파일 없음"을 에러가 아니라 **비어 있는 정상 상태(empty state)**로 그려야 한다.

### 3.2 로그 (`logs/`)

7개 파일, 공통 라인 포맷 `[YYYY-MM-DD HH:MM:SS] 메시지` (한국어).

| 파일 | 출처 |
|---|---|
| `pipeline.log` | 메인 로그 — pull(`[pull]` 접두)·process 공용 |
| `plaudpull.{out,err}.log` | pull 잡 stdout/stderr |
| `launchd.{out,err}.log` | process 잡 stdout/stderr |
| `prune.{out,err}.log` | prune 잡 (`[prune]` 접두) |

타임라인·필터에 쓸 수 있는 파싱 가능 마커:

- `[pull] 전체 {N}개 / 신규·재시도 {M}개` — pull 사이클 요약
- `처리 시작: {파일}` / `전사 엔진: AssemblyAI (화자분리)` · `WhisperX (화자분리)` · `whisper.cpp`
- `claude: 요약 요청 (model=…, 전사 {n}자)` / `gpt: 교차검증 요청 (model=…)` / `✓ GPT 교차검증 반영`
- `✓ 노트 생성: {이름}.md` / `✓ 오디오 아카이브: {이름}` / `⚠️ 아카이브 실패(…)`
- `[prune] 완료 — 삭제 N개 / X MB 확보 / 보관 K개 (보관기간 D일)`

> **제약**: 구조화(JSON) 로그가 아니며 로그 로테이션이 없다. 정규식 파싱 기반 표시임을 전제로 하고, 파싱 불가 라인은 원문 그대로 보여준다(숨기지 않는다).

### 3.3 설정 (`config.env` → `scripts/_config.py`)

사용자 설정 16키. **대시보드는 `config.env`를 직접 파싱하지 않고 `_config.py`의 로딩·마스킹 경로를 통해서만 읽는다** (아래 7.2 시크릿 계약 참조).

| 키 | 기본값 | 설명 |
|---|---|---|
| `VAULT_PATH` | (필수) | 옵시디언 볼트 루트 |
| `INBOX_DIR` | `$VAULT_PATH/_inbox` | 오디오 수신함 |
| `OUTPUT_DIR` | `$VAULT_PATH/Voice Memos` | 노트 출력 폴더 |
| `ARCHIVE_DIR` | `$HOME/Obsidian/_audio-archive` | 처리 완료 오디오 보관 |
| `WHISPER_MODEL` | `ggml-large-v3-turbo.bin` | whisper.cpp 모델 |
| `WHISPER_LANG` | `ko` | 전사 언어 |
| `PULL_INTERVAL` | `900` | pull 주기(초) — **변경 시 install.sh 재실행 필요** |
| `SUMMARY_PROMPT_FILE` | (없음) | 요약 프롬프트 오버라이드 |
| `SPEAKERS_EXPECTED` | `0` | 예상 화자 수 힌트 |
| `AUDIO_RETENTION_DAYS` | `0` | 0 = 자동 삭제 안 함 (opt-in) |
| `CLAUDE_MODEL` | `claude-opus-5` | 요약 모델 |
| `OPENAI_MODEL` | `gpt-5.2` | 교차검증 모델 |
| `ASSEMBLYAI_API_KEY` | (없음) | 🔒 시크릿 — 미설정 시 로컬 전사 |
| `HF_TOKEN` | (없음) | 🔒 시크릿 — WhisperX 화자분리 |
| `ANTHROPIC_API_KEY` | (없음) | 🔒 시크릿 — 미설정 시 요약 생략 |
| `OPENAI_API_KEY` | (없음) | 🔒 시크릿 — 미설정 시 교차검증 생략 |

### 3.4 launchd 잡 (3개)

| 라벨 | 스크립트 | 트리거 | 생존 확인 |
|---|---|---|---|
| `com.plaud-obsidian.pull` | `plaud_pull.py` | `StartInterval` = PULL_INTERVAL(900s) + RunAtLoad | `launchctl list` |
| `com.plaud-obsidian.process` | `process_inbox.py` | `WatchPaths` = INBOX_DIR + RunAtLoad | 〃 |
| `com.plaud-obsidian.prune` | `prune_audio.py` | 매일 03:00 (`StartCalendarInterval`) | 〃 |

### 3.5 출력 노트 (frontmatter)

`OUTPUT_DIR`의 노트(`{YYMMDD}_{제목슬러그}.md`, 현재 129개)에서 읽을 수 있는 메타데이터:

| 키 | 값 | 대시보드 활용 |
|---|---|---|
| `created` | 녹음일 `YYYY-MM-DD` | 목록 정렬·날짜 필터 |
| `status` | `active` \| `summary_pending` | `summary_pending` = 요약 실패, 전문만 존재 → 품질 뷰 |
| `verified` | `true` \| `false` (요약 존재 시만) | `false` = GPT 교차검증 미반영 → 품질 뷰 |
| `summary_model` | 예: `claude-opus-5` | 어떤 모델이 요약했는지 |
| `speakers` | 화자명 배열 | `?(역할)` 플레이스홀더 잔존 감지 → 품질 뷰 |
| `tags`, `type` | 상수 (`음성메모, 자동전사` / `voice-memo`) | — |

## 4. 정보 구조 (IA)

```
로컬 웹 대시보드 (127.0.0.1)
├── 1. 홈 — 파이프라인 상태      ← 랜딩, S1
├── 2. 처리 내역 (노트 목록)      ← S2
├── 3. 실패·보류 관리            ← S2, S3 (조치 버튼의 홈)
├── 4. 노트 품질 뷰              ← S5
├── 5. 로그 뷰어                 ← S2 심화
└── 6. 설정                      ← S4
```

### 화면 1 — 홈 (파이프라인 상태)

랜딩 화면. "정상인가"에 5초 안에 답한다.

- **잡 생존 배지 3개**: pull / process / prune — 로드됨·최근 종료코드 (`launchctl list` 기반). 실행 중이면 라이브 표시(lock 파일 존재).
- **파이프라인 퍼널 카운터**: 수신(pulled 136) → 수신함 대기(inbox 0) → 보류(pending 0) → 전사 실패(failed 0) → 건너뜀(skipped 1) → 노트(129) → 아카이브(10). 각 카운터 클릭 시 해당 상세 화면으로 이동.
- **최근 활동 타임라인**: `pipeline.log` 최신 N건을 마커 기반으로 아이콘화(✓ 성공 / ⚠️ 경고 / 일반).
- **이상 신호 배너** (조건부, 상단 고정): `_failed/` 격리 파일 존재, `processed_notes.txt` 잔존(아카이브 이동 실패), 시크릿 파일 권한 경고(600 아님), pending 큐 급증 등.
- **다음 pull 예정 시각** (마지막 pull 로그 + PULL_INTERVAL로 추정).

### 화면 2 — 처리 내역

생성된 노트의 목록 뷰. "그 녹음, 노트 됐나?"에 답한다.

- 테이블: 날짜(created) · 제목 · status 배지 · verified 배지 · summary_model · 전사 엔진(로그에서 역추적 가능 시).
- 필터: 날짜 범위, status, verified.
- 행 액션: **옵시디언에서 열기** (`obsidian://` URL scheme), 노트 미리보기(읽기 전용 렌더).

### 화면 3 — 실패·보류 관리

조치 액션의 홈. 세 개의 큐를 탭 또는 섹션으로 나열한다.

- **보류 큐 (pending)**: id · 시도횟수 진행바(`n/96`) · 예상 만료 시각. 액션: 시도횟수 리셋.
- **격리 목록 (`INBOX/_failed/`)**: 파일명 · 크기 · 격리 시각. 액션: 수신함 복귀(+실패 카운트 리셋).
- **건너뜀 목록 (skipped)**: id. 액션: 복구(목록에서 제거 → 다음 pull 때 재시도).
- 공통: **수동 pull 실행** 버튼 (화면 상단).

### 화면 4 — 노트 품질 뷰

요약·검증 품질 관측. 네 개의 필터 프리셋 카드 + 결과 목록.

- `status: summary_pending` — 요약 실패, 전문만 저장된 노트 (재요약 후보).
- `verified: false` — Claude 요약은 있으나 GPT 교차검증이 반영되지 않은 노트.
- 화자 미해결 — `speakers`에 `?(…)` 플레이스홀더가 남은 노트.
- **정합성 갭 리포트** — pulled id 수(136) vs 생성 노트 수(129) vs 아카이브 수(10)의 차이와, 각 차이가 어느 큐(pending/failed/skipped/미처리)로 설명되는지 대차대조표 형태로 표시. 설명 안 되는 잔여분은 "원인 불명 N건"으로 정직하게 표기.

### 화면 5 — 로그 뷰어

- 파일 선택(7개) + tail 팔로우(자동 갱신) + 라인 수 선택.
- 레벨 필터: 전체 / ✓ 성공 / ⚠️ 경고·에러 (마커 기반).
- 텍스트 검색. 파싱 불가 라인은 원문 그대로.

### 화면 6 — 설정

- 3.3의 16키를 그룹핑해 표시: 경로 / 전사 / 요약·검증 / 운영(주기·보존).
- **시크릿 4키는 값 대신 "설정됨 / 미설정" 상태만 표시** — 값 입력은 가능하되 표시·재표시는 불가(write-only).
- 저장 시 부작용 안내: `PULL_INTERVAL` 변경 → "적용하려면 `bash install.sh` 재실행 필요(플리스트 재생성)" 인라인 경고. 경로 변경 → 기존 파일이 이동되지 않음을 명시.
- 각 시크릿 옆에 파생 효과 설명: "미설정 시 → 로컬 전사로 폴백" 등 (graceful degradation을 설정 UI에서 학습 가능하게).

## 5. 기능 요구사항 (우선순위)

P0 = 없으면 대시보드 무의미 / P1 = 1차 릴리스 포함 / P2 = 후속.

| ID | 화면 | 요구사항 | 우선순위 |
|---|---|---|---|
| F-01 | 홈 | 잡 3개 생존 배지 + 마지막 실행 결과 | P0 |
| F-02 | 홈 | 퍼널 카운터 7종 (클릭 시 상세 이동) | P0 |
| F-03 | 홈 | 최근 활동 타임라인 (pipeline.log 파싱) | P0 |
| F-04 | 홈 | 이상 신호 배너 (격리·아카이브 실패·권한 경고) | P1 |
| F-05 | 처리 내역 | 노트 목록 + status/verified 배지 + 필터 | P0 |
| F-06 | 처리 내역 | 옵시디언 열기 링크, 노트 미리보기 | P1 |
| F-07 | 실패·보류 | pending/failed/skipped 3개 큐 조회 | P0 |
| F-08 | 실패·보류 | 조치 액션 4종 (6장 표 참조, 확인 다이얼로그 포함) | P1 |
| F-09 | 품질 뷰 | 4개 필터 프리셋 (summary_pending / unverified / 화자? / 정합성 갭) | P1 |
| F-10 | 로그 뷰어 | tail + 레벨 필터 + 검색 | P1 |
| F-11 | 설정 | 16키 조회 (시크릿 마스킹) | P1 |
| F-12 | 설정 | 값 수정 + 부작용 인라인 경고 | P2 |

## 6. 조치 액션과 안전장치

모든 액션은 **명시적 확인 후 실행**이 기본이다. 파괴적 액션(삭제)은 이 프로젝트 전역 규칙상 **사용자 명시 동의 없이는 절대 실행하지 않는다.**

| 액션 | 동작 | 안전장치 | 되돌림 |
|---|---|---|---|
| 격리 파일 재시도 | `_failed/` → INBOX 복귀 + `transcribe_failures.txt` 카운트 리셋 | 확인 다이얼로그 ("3회 실패했던 파일입니다") | 다시 실패하면 재격리됨 |
| pending 강제 재시도 | `pending_ids.txt` 시도횟수 리셋 | 확인 | 자연 만료(96회) 재개 |
| skipped 복구 | `skipped_ids.txt`에서 해당 id 제거 | 확인 + 대상 id 명시 | pull이 다시 skip 판정 가능 |
| 수동 pull 실행 | `launchctl kickstart` (pull 잡) | 실행 중이면 flock이 중복 방지 — UI는 "이미 실행 중" 상태로 비활성화 | — |
| 아카이브 정리 미리보기 | prune **dry-run** 결과 표시 (삭제 대상 목록·용량) | **실제 삭제는 대상 목록 확인 + 명시적 재확인 후에만**. `AUDIO_RETENTION_DAYS=0`이면 기능 자체 비활성 | 불가 (삭제는 영구) — 그래서 이중 확인 |
| 재요약 (P2) | `summary_pending` 노트의 전사로 요약 재요청 | **API 비용 고지** ("Claude+GPT 호출 발생, 예상 입력 n자") + 확인. 중복 노트 생성 금지(기존 노트 갱신) | 기존 노트 백업 후 갱신 |

UX 원칙:
- 확인 다이얼로그는 **무엇이 어떻게 바뀌는지 구체적으로** 명시한다 ("skipped에서 id abc…를 제거합니다. 다음 pull 주기에 다시 다운로드를 시도합니다").
- 액션 실행 결과는 토스트로 끝내지 않고 해당 큐 화면의 상태 변화로 확인 가능해야 한다.
- 실행 중 잠금(lock 파일 존재) 상태에서는 충돌 가능 액션을 비활성화하고 이유를 표시한다.

## 7. 비기능 요구사항

### 7.1 네트워크·격리

- **127.0.0.1 바인딩 전용.** 0.0.0.0 바인딩 금지, 외부망 노출 금지.
- 대시보드 프로세스는 파이프라인과 완전 분리 — **대시보드가 죽어도 파이프라인은 무관하게 동작**한다. 상시 데몬을 새로 만들기보다 필요할 때 띄우는 형태를 지향한다(파이프라인 본체의 "no daemons" 철학 유지).

### 7.2 시크릿 계약 (절대 규칙)

- `*_KEY` / `*_TOKEN` 값은 **어떤 화면·응답·로그에도 노출하지 않는다.** 표시는 "설정됨/미설정"뿐.
- 설정 읽기는 `config.env` 직접 파싱이 아니라 `scripts/_config.py`의 로딩 경로(`is_secret_key`/`mask_secrets`)를 재사용한다.
- 브라우저로 내려가는 API 응답에도 시크릿 값이 실리지 않는다 (마스킹은 서버 측에서).

### 7.3 파이프라인 불변식 보호

- 조회는 상태 파일·로그의 **읽기 전용** 접근. 파이프라인의 flock·atomic 쓰기 계약을 깨지 않는다.
- 쓰기 액션(6장)은 기존 상태 파일 포맷(탭 구분·정렬·`.tmp`+`os.replace` atomic rewrite)을 그대로 따른다.
- 상태 파일을 수정하는 액션은 해당 파이프라인 스크립트가 실행 중(lock 존재)일 때 대기 또는 거부한다.

### 7.4 기술 제약 (참고)

- 기술 스택은 이 PRD에서 강제하지 않는다. 단, 리포 본체는 "Python stdlib-only" 원칙이므로, 구현 시 stdlib `http.server` 기반 단일 파일 서버 + 정적 프런트 같은 최소 의존 접근을 우선 검토할 것.
- 데이터 갱신은 폴링(수 초 간격)으로 충분하다. WebSocket 등 실시간 인프라는 요구하지 않는다.

### 7.5 표시 언어

- UI·라벨·메시지는 **한국어** (리포 컨벤션과 동일).
